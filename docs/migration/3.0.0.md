# Migrating to App Toolkit 3.0.0: navigation

3.0.0 replaces the Toolkit's navigation with a one-activity shell. The old navigation is removed,
not deprecated: code that used it no longer compiles. This guide maps each removed API to its
replacement and walks through moving an app over. `:sample:app` is a complete example of the result.

The module READMEs hold the details:

- [`:library:navigation`](../../library/navigation/README.md): the graph, navigator, scenes,
  transitions, predictive back and the Toolkit's keys.
- [`:library:shell`](../../library/shell/README.md): `ShellHost` and the chrome.
- [`:library:core:ui`](../../library/core/ui/README.md#page-frame): the page frame.
- [`:library:apptoolkit`](../../library/apptoolkit/README.md#navigation): `toolkitGraph { }` and
  the Toolkit's pages.
- [`:library:feature:developer`](../../library/feature/developer/README.md): the developer options.
- Each feature's README: the page it registers, its key and its provider contract.

## What changes for an app

The fixed Permissions catalogue no longer has a data-loading graph. Keep `permissionsPage()`,
`PermissionsScreen()` and the public `PermissionsContent` rendering entry point.
Remove manual `permissionsModule` registration and dependencies on `PermissionsRepository`,
`DefaultPermissionsRepository`, `PermissionsViewModel`, `PermissionsUiState` or `PermissionsEvent`.
The standard `appToolkitModules` graph already omits these bindings. Text is resolved in Compose
against the current locale, with no reload operation.

The shared `adsEnabledFlow` now starts `false` until storage answers. Do not treat `.first()` as
proof that a persisted read has completed, cache that initial value forever, or substitute a local
enabled default. Continue observing the shared source as `AppOpenAdController` does. Transient IO read
failures disable ads and retry with delays capped at 30 seconds; unexpected failures are logged
and remain disabled until the source is recreated. `defaultAdsEnabled` applies when a successful
read finds no key, not while a read is pending.

The default back-edge style is `BackEdgeStyle.System`. Explicitly stored developer overrides are
preserved; resetting developer options selects the system style.

When adopting the sample's activity-resume integrations, also copy the consent retry handling in
[`sample/app/README.md`](../../sample/app/README.md#architectural-decisions). The app owns its
`MainViewModel`, so a library upgrade alone cannot update this policy:

```kotlin
try {
    consentRepository.requestConsent(host)
} catch (error: ConsentException) {
    if (error.reason != ConsentException.Reason.HOST_UNAVAILABLE) throw error
    hasRequestedConsent = false
    // Keep a breadcrumb, then leave this launchReport block. A later resume retries.
    return@launchReport
}
```

Keep this catch inside `launchReport`, before its generic error reporting, and keep the guard set
while a request is running or has completed. Only host unavailability clears it. This automatic
request policy does not replace error handling for an explicitly opened privacy form. The shared
library also keeps ad network failures as breadcrumbs rather than nonfatal reports; consumer apps
receive that change when they upgrade to a library release containing it.

Before, an app built its own main screen: a `NavDisplay` over a `NavigationState`, entry builders
from each feature and `appToolkitNavigationEntryBuilders`, a `BottomNavigationBar` or
`LeftNavigationRail`, a `NavigationDrawerSheet` filled by a `NavigationRepository`, and a
`MainTopAppBar`. Toolkit screens such as Settings, Help and Support opened as activities, and the
first launch went through `StartupActivity` and `OnboardingActivity`.

Now an app declares a graph once, and `ShellHost` draws everything: the app bar, the navigation bar,
rail or drawers for the window size, the overflow menu, the transitions and the back gesture.
Screens move with `LocalShellNavigator.current.navigate(key)`.

## Step by step

### 1. Make your keys serializable

Every key becomes a Navigation 3 `NavKey` annotated with `@Serializable`. Apply the Kotlin
serialization plugin in each module that declares keys.

```kotlin
// Before
@Parcelize
data object HomeRoute : StableNavKey {
    override val destinationType get() = NavigationDestinationType.TopLevel
}

// After
@Serializable
data object HomeRoute : NavKey
```

`destinationType` is gone. Whether a key is a tab, a child pushed on a tab, or a page over the
shell is declared in the graph instead.

### 2. Declare the graph

Replace entry builders, bottom bar items and drawer items with one graph. `toolkitGraph { }` adds
the Toolkit's pages; use `shellGraph { }` from `:library:navigation` for an app that does not use
`:library:apptoolkit`.

```kotlin
val graph = toolkitGraph(appTitle = R.string.app_name, appIcon = ToolkitIcon.Resource(R.drawable.app_logo)) {
    tab(HomeRoute, R.string.home, ToolkitIcon.AnimatedVector(R.drawable.anim_home)) {
        HomeScreen(paddingValues = contentPadding())
    }
    tab(
        key = LibraryRoute,
        label = R.string.library,
        icon = ToolkitIcon.Vector(Icons.Outlined.VideoLibrary),
        search = TabSearch(hint = R.string.search_library),
        fabs = { listOf(ToolkitFab(ToolkitIcon.Vector(Icons.Outlined.Add), onClick = ::add, label = stringResource(R.string.add))) },
    ) { LibraryScreen() }
    child<ItemRoute>(title = { it.name }) { item -> ItemScreen(item) }
    page<AboutAppRoute>(title = { stringResource(R.string.about) }) { AboutAppScreen() }

    drawer {
        link(DownloadsRoute, R.string.downloads, ToolkitIcon.Vector(Icons.Outlined.Download))
        // Settings, Help and feedback, Updates and Share: always last, pinned to the bottom.
        toolkitFooter(onShowUpdates = { showChangelog = true })
    }
    overflow { supportUs() }
    deepLinks { action(ACTION_OPEN_SETTINGS) { SettingsRoute } }
}
```

### 3. Host it

`ShellHost` replaces the app's main screen composable. Keep the theme, the splash screen and the
work that needs the activity (consent, review, update) in the activity.

```kotlin
setContent {
    AppTheme {
        ShellHost(
            graph = graph,
            resolveStart = {
                if (dataStore.startup.first()) StartupRoute
                else displayPreferences.startupValueFlow(HomeRoute.ROUTE_ID, ::startKeyFor).first()
            },
            onReady = { keepSplashVisible = false },
        )
    }
}
```

Declare the activity `launchMode="singleTop"` (or keep `singleTask`) so intents that arrive while it
runs reach the shell. It is the launcher activity now: remove any launcher filter from a
`StartupActivity` you declared, since the Toolkit no longer has one.

The first launch is two start screens, `StartupRoute` (permissions and consent) and
`OnboardingRoute`. Start on `StartupRoute` while onboarding is not done, as above; finishing
onboarding enters the shell on its start tab.

### 4. Pad lists by the shell's bars

Tabs are drawn behind the navigation bar, banner and player so lists scroll under them. Add
`contentPadding()` to a scrolling list's content padding, or pad a screen that does not scroll by
`LocalContentPadding.current`.

```kotlin
LazyColumn(contentPadding = contentPadding(PaddingValues(bottom = 16.dp))) { ... }
```

### 5. Navigate by key

Replace `NavigationManager`-style request channels, `Context.openActivity` (now removed) for Toolkit
screens, and back-stack helpers with the navigator:

```kotlin
val navigator = LocalShellNavigator.current
navigator.navigate(LicensesRoute)
navigator.goBack()
```

## Native ad placement defaults

`BottomAppBarNativeAdBanner` now defaults to `enabled = false`. Existing calls without this flag
render nothing and request no ad. To retain a host placement, explicitly pass `enabled = true` and
review its proximity to navigation and other app controls. Keep `onAdLoaded` as a named argument
or trailing lambda; it now follows `enabled` in the parameter list.

`NoDataScreen` keeps its existing `showAd = true` default and `NO_DATA_NATIVE_AD` binding requirement.

The sample retains its bottom-bar native ad placement, unit ID, and binding, with `enabled = false`.
Ads explicitly placed within scrolling content remain available. Review the
[placement warning and Google source links](../../library/integration/ads/README.md#placement-warning-and-explicit-opt-in)
before enabling the optional bottom-bar placement.

### Telemetry

`FirebaseController` is now `TelemetryRepository`, in `core.common.telemetry`: the contract names
no vendor, and telemetry is not a data repository. 3.0.0-pre25 removed the old names, which earlier
previews kept as deprecated aliases; replace each import and type.

| Old | New |
|---|---|
| `core.common.data.repositories.FirebaseController` | `core.common.telemetry.TelemetryRepository` |
| `core.common.data.repositories.TelemetryRepository` | `core.common.telemetry.TelemetryRepository` |
| `core.common.data.repositories.NoOpTelemetryRepository` | `core.common.telemetry.NoOpTelemetryRepository` |
| `core.common.data.models.analytics` (`AnalyticsEvent`, `AnalyticsValue`) | `core.common.telemetry.models` |
| `integration.firebase.data.repositories.DefaultFirebaseController` and `FirebaseControllerImpl` | `integration.firebase.data.repositories.FirebaseTelemetryRepository` |
| `core.testing.FakeFirebaseController` | `core.testing.FakeTelemetryRepository` |
| a `firebaseController` parameter | a `telemetryRepository` parameter |

A ViewModel built with `firebaseController = ...`, such as a Koin binding with
`firebaseController = get()`, changes to `telemetryRepository =`, and a binding of the type itself,
`single<FirebaseController>`, to `single<TelemetryRepository>`. Most apps migrate with two
replacements across their sources:

```text
core.common.data.repositories.TelemetryRepository  ->  core.common.telemetry.TelemetryRepository
core.common.data.repositories.FirebaseController   ->  core.common.telemetry.TelemetryRepository
```

then rename the remaining `FirebaseController` type references to `TelemetryRepository`.

Composables no longer take it at all. `ScreenHost`, `GeneralButton`,
`CommonFilterChip`, `GeneralTextField`, `DatePickerTextField`, `DropdownMenuBox`,
`CommonDropdownMenuItem`, `AnimatedIconButtonDirection`, the animated FABs, `TopListFilters` and
every preference row read `LocalTelemetry` instead: delete the `firebaseController = ...` argument
and keep the `ga4Event`. A screen that logged its own events with an injected one reads
`LocalTelemetry.current` instead of `koinInject()`.

`ShellHost` provides `LocalTelemetry` from the app's Koin binding. A composition the app starts
outside it, such as a dialog window or a `ComposeView` of its own, wraps its content in
`ProvideTelemetry { }`; without it the events there are dropped, not reported. Read it as
`val telemetry = LocalTelemetry.current`.

#### Analytics stay in the UI layer

`TelemetryRepository` is now three contracts in one: `AnalyticsReporter` for GA4 events, screen
views and user properties, `DiagnosticsReporter` for breadcrumbs and non-fatal reports, and
`TelemetryCollection` for the consent-driven collection switches. ViewModels and composables keep
using `TelemetryRepository`. Code under `data/` and `domain/` takes `DiagnosticsReporter`, and
`TelemetryCollection` where it applies consent, and never reports analytics: it returns the outcome,
and the screen or ViewModel reports the event. `checkModuleBoundaries` enforces this in the Toolkit
and the sample; apply the same rule in an app.

The Toolkit's repositories changed their parameter to `diagnostics: DiagnosticsReporter`, and
`DefaultConsentRepository` to `diagnostics` and `collection: TelemetryCollection`. A Koin binding
with `telemetryRepository = get()` for one of them changes the argument name; `get()` resolves the
narrower type. The GA4 helpers such as `logSelectContent` and `logUnlockAchievement` extend
`AnalyticsReporter`, so they still work on a `TelemetryRepository`.

`telemetryModule` binds the three contracts to the app's one `TelemetryRepository`, so Firebase is
set up once and a host that replaces `TelemetryRepository` replaces all three. `appToolkitModules`
includes it. An app that assembles its own module list adds `telemetryModule` beside the module that
binds `TelemetryRepository`; without it, a repository asking for `DiagnosticsReporter` fails to
resolve.

## Screen tracking

`ScreenHost` replaces `TrackScreenView`, `TrackScreenState` and the `MessageHost(viewModel)` a
screen called beside them. Declare each screen once as a `TrackedScreen` (in
`core.common.telemetry.models`), with the same name and class literals it reported before, so
dashboards keep their history:

```kotlin
// Before
TrackScreenView(screenName = "News", screenClass = "NewsScreen")
TrackScreenState(screenName = "News", state = state.articles)
NewsScreenContent(state = state, onEvent = viewModel::onEvent)
MessageHost(viewModel = viewModel, onAction = { viewModel.onEvent(NewsEvent.Load) })

// After
private val NEWS_SCREEN = TrackedScreen(name = "News", className = "NewsScreen")

ScreenHost(
    screen = NEWS_SCREEN,
    status = state.articles,
    viewModel = viewModel,
    onMessageAction = { viewModel.onEvent(NewsEvent.Load) },
) {
    NewsScreenContent(state = state, onEvent = viewModel::onEvent)
}
```

- A screen with nothing that loads passes no `status`, and one without a ViewModel no `viewModel`.
  Do not build a `Loadable.Ready` only to report a status; the Toolkit's Permissions page no longer
  does, so it stops sending a `screen_state` of `success`.
- A screen whose messages show in a snackbar host of its own, or as toasts, keeps calling
  `MessageHost` or its own code and passes no `viewModel`.
- `ScreenStateHandler` still renders each `Loadable` inside the content. An `onEmpty` or `onError`
  that only copies `NoDataScreen` to change its icon, add a retry or hide the ad becomes a
  parameter (nothing breaks if it stays):

  ```kotlin
  // Before
  ScreenStateHandler(
      state = state.files,
      onRetry = onRetry,
      onEmpty = { empty -> NoDataScreen(icon = Icons.Outlined.Folder, message = empty.message?.asString(), showRetry = true, onRetry = onRetry, paddingValues = contentPadding) },
      onError = { failed -> NoDataScreen(icon = Icons.Outlined.Folder, message = failed.message.asString(), isError = true, showRetry = failed.retryable, onRetry = onRetry, paddingValues = contentPadding) },
  ) { ready -> FileList(ready.value) }

  // After
  ScreenStateHandler(
      state = state.files,
      contentPadding = contentPadding,
      onRetry = onRetry,
      retryWhenEmpty = true,
      icon = Icons.Outlined.Folder,
  ) { ready -> FileList(ready.value) }
  ```

  `showAd = false` hides the native ad. An app with loading, empty or failed content of its own
  everywhere provides it once through `LocalScreenStates` instead of passing it to every handler.
- Screen views now follow visibility. A screen is reported once it is visible and active, not each
  time it enters composition, so views no longer count transition frames, rotations or a cancelled
  back gesture, and do count each return from the background. Expect slightly different
  `screen_view` totals from earlier previews.
- `screen_state` is reported at the start of each visit and when the label changes, with the same
  event and parameters as before. A label that did not change is no longer sent again.

## Toolkit screens

Every Toolkit screen is a page of the shell. `toolkitGraph { }` calls `toolkitPages()`, which calls
each feature's registration (`settingsPage()`, `displaySettingsPage()`, `aboutPages()`,
`permissionsPage()`, `onboardingPages()` and the others; the
[`:library:apptoolkit` README](../../library/apptoolkit/README.md#navigation) lists them with their
keys and pane roles). To replace a page, register the same key in your builder; the Toolkit's page
is then skipped. To pass a registration arguments, call it yourself first:

```kotlin
toolkitGraph(appTitle = R.string.app_name) {
    aboutPages { AboutScreen(onVersionTap = { taps -> unlockAfter(taps) }) }
}
```

Offer the pages where you want them: `toolkitFooter(...)` in the drawer (Settings, Help, Updates
and Share, always last), `supportUs()` in the overflow menu, or `navigate(key)` from a button.
Beside a rail or a permanent drawer, pages open next to the navigation, which stays in place.

### Floating action buttons

Describe a screen's buttons instead of drawing them, and the Toolkit's scaffolds stack them in a
column with the Toolkit's feedback: `fabs = { listOf(ToolkitFab(...)) }` on a tab, child or page,
or `ScaffoldFabs(listOf(...))` from the screen for buttons that follow its state. A holder object
that forwarded a screen's action to a tab's `fab` slot, as the sample's `RandomAppAction` did, is no
longer needed.

### Settings rows

Settings rows open keys. A row whose click the app wants to handle, such as opening the system's
notification settings, passes an `action` that returns whether it handled it:

```kotlin
SettingsPreference(
    key = "notifications",
    title = context.getString(SettingsR.string.notifications),
    destination = PrivacySettingsRoute,
    action = { context.openAppNotificationSettings() },
)
```

### Permission usage

Android's permission manager and privacy dashboard show an information icon beside an app that
explains its permissions. The Toolkit's `PermissionsActivity` used to answer it with the
permissions list; `:library:apptoolkit` now declares `PermissionUsageActivity`, which answers it
with the privacy page, over the system's settings. Nothing to declare. Remove an alias or activity
of your own for `VIEW_PERMISSION_USAGE`, or the system has two to choose from; to keep yours
instead, remove the Toolkit's with `tools:node="remove"` (see the
[`:library:apptoolkit` README](../../library/apptoolkit/README.md#permission-usage)).

### Snackbars

A screen's snackbars belong to the Toolkit scaffold around it, a page's frame or the shell's tabs,
which draws them above its bottom chrome. Show them with `rememberScaffoldSnackbars()`, or with
`DefaultSnackbarHandler`, which now uses the scaffold's host when given none and never draws a
second one. `rememberPageSnackbarHostState()` still returns that host for code written against
Material's `SnackbarHostState`.

### Features no longer depend on each other

A Toolkit feature opens another's page by key, and shares a contract through `:library:core:ui` and
Koin: the advanced settings resolve `IssueReporterSheet` with `getOrNull()` and hide the bug report
when no module binds it. An app that depended on a feature to reach another (for example on
`:library:feature:settings` for the diagnostics screen) now depends on each module it uses, or on
`:library:apptoolkit`.

### ViewModels and screen state

Every Toolkit ViewModel is on `core.ui.screen`. An app that only registers the Toolkit's pages
needs nothing here. Code that drives a Toolkit ViewModel or calls its screen directly changes:

- Read `state` instead of `uiState`, and show `messages` with `MessageHost(viewModel)`. A field that
  loads is a `Loadable`: its value is in `Loadable.Ready`. `actionEvent` is gone with the `XAction`
  contracts; a page now navigates from its screen.
- Send `Load` instead of `Initialize` (`DisplaySettingsEvent`, `ThemeSettingsEvent`,
  `UsageAndDiagnosticsEvent`). `OnboardingThemeEvent.Initialize`, `OnboardingEvent.ObserveCompletion`
  and the `DismissSnackbar` events are gone; the ViewModels start on their own.
- `AdvancedSettingsScreen()`, `PrivacyScreen()`, `UsageAndDiagnosticsScreen()`,
  `DisplaySettingsScreen()`, `ThemeSettingsScreen()` and `StartupScreen()` take no parameters and
  pad by `contentPadding()`. Register `startupPage()` rather than calling
  `StartupScreen(screenState, onContinueClick)`.
- A Koin binding written by hand drops `dispatchers = get()` from `AdvancedSettingsViewModel`,
  `UsageAndDiagnosticsViewModel`, `DefaultUsageAndDiagnosticsRepository`, `AdsSettingsViewModel`,
  `DefaultIssueReporterRepository` and
  `IssueReporterViewModel`
  (which also drops `sendIssueReport`). `OnboardingViewModel` and `StartupViewModel` take
  `consentRepository = get()`, which `appToolkitModules` binds.
- `SupportViewModel.onDonateClicked(activity, id)` is
  `onEvent(SupportEvent.Donate(productId = id, activity = activity))`, and `SupportScreenUiState`
  and `DonationOptionUiState` are `SupportUiState` and `ui.models.DonationOption`.
- `DisplaySettingsViewModel.startupRoute(defaultRoute)` is `DisplaySettings.startupRoute` in its
  state, and `FirebaseConsentDialog` takes `settings = ...` instead of the UI state.

A repository an app implements throws instead of returning `DataState`:

- `CacheRepository.clearCache()` is a `suspend` function that throws a `StorageException`;
  `storageCall { }` from `core.datastore.data.local.extensions` wraps the work.
- `AdsSettingsRepository.setAdsEnabled` and `setReduceAds` return nothing and throw a
  `StorageException`, its flows fail with one, and it no longer declares `defaultAdsEnabled`.
- `ConsentRepository.requestConsent` suspends and throws a `ConsentException`; see the
  `ConsentRepository` entry in the changelog.
- `IssueReporterRepository.sendReport` returns the issue URL and throws an
  `IssueReportRejectedException` or a `NetworkException`. Code that called `SendIssueReportUseCase`
  calls the repository. An exhaustive `when` over `IssueSubmissionState` needs a `Failed` branch.
- A host that embedded `IssueReporterContent` shows `IssueReporterBottomSheet` instead.

### Screen entrances

Each `ScreenHost` times its own entrance, and the Toolkit's components enter on their own, so a
screen needs little motion code of its own:

- Replace `items { Modifier.animateItem().animateVisibility(index = i) }` with `animatedItems`,
  `animatedItemsIndexed` or `animatedItem`, which do both on the app's motion scheme. Keep an item
  that holds only filter chips or a native ad a plain `item`.
- Remove `animateVisibility` from preference rows, switch cards, grouped action lists, info
  messages, filter chips, `NoDataScreen` and native ad slots; they enter by themselves.
- Pass no durations or springs of your own: read `MaterialTheme.motionScheme`, so the app's
  `MotionTempo` sets the pace. The default tempo is `Calm`; set `motionTempo = MotionTempo.Standard`
  in `appToolkitDefaults { shell { } }` to keep Material's expressive pace.
- Entrances play each time a screen is opened, not on going back to it. Set
  `entranceReplay = EntranceReplay.EveryVisit` to replay them on every return, or
  `EntranceReplay.FirstVisit` to play them once per screen while the app runs.
- Draw a screen's loading through `ScreenStateHandler`, in `onLoading` or the app's
  `ScreenStates.loading`, not beside it: the handler keeps it on screen until the content can
  enter, so a result that arrives during the transition never leaves the screen blank.
- An app that set `ScreenStates(transition = ...)` keeps its own; leave it out to cross-fade on the
  motion scheme.

## Developer options

The shell's layout choices are display settings: app bar and bottom bar style, labels, hiding on
scroll, the navigation colour, content width, tab transition and back swipe. Each is
offered only when the app's graph uses it.

`DeveloperOptionsRoute` opens what is left for testing: where the app starts, a forced navigation
layout, the bottom accessories, the animation speed and a live view of every back stack. The
advanced settings list it once the About screen's version easter egg is found, so an app needs no
drawer entry for it; remove one it had.

### App defaults

An app that wants other defaults than the Toolkit's, such as the follow-finger back swipe or
collapsed large app bars on every page, declares them once with `appToolkitDefaults { }` and passes
`defaults.navigation` to `toolkitGraph` and `defaults.shell` to `ShellHost`. Do not write them into
`ShellPreferencesRepository` at launch: that would overwrite what people chose. See the shell README's
[App defaults](../../library/shell/README.md#app-defaults).

`tab`, `child`, `page` and `pageIfAbsent` take a nullable `topBar`, null meaning the app's default
for that kind of destination. A call that passed a style is unchanged. Resetting the developer
options now returns to the app's defaults. A custom `ShellPreferencesRepository` that should do the same
overrides `defaults`.

## Checklist

- Every key is `@Serializable` and registered in the graph; building the graph fails for a
  tab or start that is not registered, and `keyFor` drops deep links to unregistered keys.
- The activity hosts `ShellHost` inside `AppTheme`, with edge-to-edge enabled.
- Lists pad by `contentPadding()`.
- Nothing starts a Toolkit activity or calls `openActivity`; first launch starts on `StartupRoute`
  from `resolveStart`, and the manifest declares nothing for `VIEW_PERMISSION_USAGE`.
- Nothing imports the `core.common` packages listed under [Moved APIs](#moved-apis), or
  `feature.changelog.ui.views.dialogs.ChangelogDialog`.
- A custom `PermissionsRepository` returns `SettingsConfig`, not `Flow<SettingsConfig>`, and a
  custom `CacheRepository`, `AdsSettingsRepository`, `ConsentRepository` or
  `IssueReporterRepository` throws instead of returning `DataState`.
- Nothing reads a Toolkit ViewModel's `uiState` or `actionEvent`, or passes `paddingValues` to a
  Toolkit screen; see [ViewModels and screen state](#viewmodels-and-screen-state).
- Nothing names `FirebaseController`, `DefaultFirebaseController`, `FirebaseControllerImpl`,
  `core.common.data.repositories.TelemetryRepository` or a `firebaseController` parameter, and no
  composable is passed one; see [Telemetry](#telemetry).
- Lists enter with `animatedItems` or `animatedItem`, and no Toolkit component is wrapped in
  `animateVisibility`; see [Screen entrances](#screen-entrances).
- No screen calls `TrackScreenView` or `TrackScreenState`; every screen is a `ScreenHost`, see
  [Screen tracking](#screen-tracking).
- Every composition outside `ShellHost` is wrapped in `ProvideTelemetry { }`.
- Nothing imports `navigation.models`, `navigation.ui`, `navigation.backstack`,
  `navigation.animations`, `navigation.data` or `core.ui.navigation`.

## Preference source ownership

Ads and review preference interfaces and implementations move from `core.datastore.data.local` to
`integration.ads.data.local` and `integration.review.data.local`. Onboarding and changelog sources
move to `feature.onboarding.data.local` and `feature.changelog.data.local`.

All owners receive the same `DataStore<Preferences>` binding. The settings filename, keys, defaults
and migrations are unchanged. Keep `dataStoreModule` and the owning feature/integration modules in
custom graphs. Register each source once; in particular, the ads source owns an eager collector.

The `AdsSettingsRepository` and `OnboardingRepository` interfaces move to
`core.common.data.repositories`, so core UI and host core modules can consume them independently
of implementation modules. Implementations remain in ads and onboarding. Ads UI and initialization
share `AdsSettingsRepository.adsEnabled`; cold settings reads still propagate storage failures.

`CommonDataStore` is removed, along with `CommonDataStoreCore` and `rememberCommonDataStore`. The
file stays: `Context.commonDataStore`, bound by `dataStoreModule` as `DataStore<Preferences>`. Each
preference now belongs to a module, under the same key:

| Was on `CommonDataStore` | Now |
|---|---|
| theme mode, AMOLED, dynamic colors, palettes | `ThemePreferencesRepository` |
| startup page, bottom bar labels, bouncy buttons, language | `DisplayPreferencesRepository` |
| `startupValueFlow` (`core.datastore.data.local.extensions`) | `DisplayPreferencesRepository.startupValueFlow` (`core.datastore.utils.extensions`) |
| ads, reduce ads, `adsEnabledFlow` | `AdsSettingsRepository` (`adsEnabled`) |
| startup (first run) | `OnboardingRepository.observeOnboardingCompletion()`, its inverse |
| usage and diagnostics, the four consents | `UsageAndDiagnosticsPreferencesDataSource` and `ConsentPreferencesDataSource` in `integration.consent.data.local` |
| `lastUsed`, `settingsInteracted` | Removed; nothing read them |
| `favoriteApps`, `componentsShowcaseUnlocked` | Removed from the Toolkit; an app keeps them in its own source over `DataStore<Preferences>` with the keys `favorite_apps` and `components_showcase_unlocked` |

An app that subclassed or wrapped `CommonDataStore` keeps its own keys in a data source over the
graph's `DataStore<Preferences>`, and binds the Toolkit's contracts, such as
`OnboardingPreferencesDataSource`, to the Toolkit's own sources rather than to that wrapper.
The ads source is closed through its owning Koin binding.

`AppOpenAdController` now requires `adsSettingsRepository` rather than `dataStore`.
`DefaultAdsSettingsRepository`, `DefaultReviewRepository` and `DefaultOnboardingRepository` take
their own preference source as `preferences`. `DefaultIssueReportHistoryRepository` takes an
`IssueReportHistoryDataSource` as `preferences` instead of a `DataStore`. `AppTheme` consumes ads, display and theme repository
bindings. Source access remains in the data layer.

## pre27 to pre28

The shared settings binding is now qualified. Custom sources and overrides must use:

```kotlin
get<DataStore<Preferences>>(qualifier = named(DataStoreQualifiers.SETTINGS))
```

Import `DataStoreQualifiers` from `core.datastore.di`. An unqualified host store can coexist with
this binding. Continue using the same Toolkit settings file; no stored keys or defaults move.

To start a build with ads disabled when no saved choice exists, pass `defaultAdsEnabled = false`
to `appToolkitModules`, `appToolkitFoundationModules` or `adsIntegrationModule`. Remove local
ads-source overrides whose only purpose was changing that default.

| --- | --- |
| `ShellPreferences` and its Context factory | `ShellPreferencesRepository` and its Context factory |

The next pre28 consistency pass adds two source requirements: implement
