## Compose: a concrete upstream fix candidate

The [1.13.0-beta01 release notes](https://developer.android.com/jetpack/androidx/releases/compose-ui#1.13.0-beta01)
describe a fix for deactivated layout nodes remaining in the layout queue and crashing during
remeasure (change `Ie64a5`). The actual AAR comparison confirms this change:

* In `1.12.1`, `AndroidComposeView.onLayoutNodeDeactivated` updates autofill state, but does not
  notify `MeasureAndLayoutDelegate` to remove the node from its queues.
* In `1.13.0-beta01`, it first calls `MeasureAndLayoutDelegate.onNodeDeactivated`.
* That new method removes the node from both `relayoutNodes` and `onPositionedDispatcher`.
* Both versions still reject remeasurement of a deactivated node. The beta fixes queue cleanup
  rather than swallowing the precondition failure.

This is a strong candidate for the readable emulator stack in
[the Compose incident](open/compose-measure-deactivated-node-exception/README.md). It does not yet
prove that every reported occurrence has the same cause or that the historical OnePlus failure
is resolved.

The next useful experiment is an aligned Compose beta upgrade, followed by a build, affected
screen tests, rapid filtering/category changes, scrolling, background/resume and predictive back.
Do not replace only `ui-android` inside an otherwise stable Compose graph: internal JVM method
names differ between these inspected versions (for example, `$ui` and
`$androidx_compose_ui_ui`). Check the complete resolved Compose family before runtime validation.

The beta AAR declares `minCompileSdk=37`, `minCompileMinorSdk=1` and
`minAndroidGradlePluginVersion=9.1.0`. This checkout already uses AGP `9.4.1` and Kotlin `2.4.21`,
but at the time of this audit its integer `COMPILE_SDK=37` did not select the required minor
platform. A subsequent build change adds `COMPILE_SDK_MINOR=1` and wires `compileSdkMinor`
through the Android modules, selecting SDK 37.2 without changing the Compose dependencies.
Consumers of the proposed Compose beta would inherit the new compile
SDK requirement. A stable upstream backport is the lower migration cost option when available;
the current official release page still lists `1.12.1` as stable.

## Billing: narrow activity recovery is possible, but needs purchase validation

`ProxyBillingActivity` in `9.1.0` is public and non-final. Its initial `onCreate(null)` path reads
`BUY_INTENT` or `IN_APP_MESSAGE_INTENT`, then calls `PendingIntent.getIntentSender`. Missing extras
or a null parcelable can reach that call with a null pending intent. Its exception table catches
`SendIntentException` for this launch, not `NullPointerException`.

Expanded `configChanges` cannot validate the initial intent. Repository-level catches around
`launchBillingFlow` cannot catch a later framework activity callback either. The
[official Billing release notes](https://developer.android.com/google/play/billing/release-notes)
list `9.1.0` as the newest release reviewed; an upgrade is not currently an established fix.

A possible local mitigation is a narrowly guarded subclass, keeping the SDK's component name via
an activity alias. It must recover only the confirmed malformed initial envelope and preserve
valid launches, saved-state restoration, cancellation callbacks and receiver cleanup. The sample
widget's guarded Glance trampoline demonstrates the alias pattern, but does not establish that
Billing supports it. This would depend on SDK internals, so it needs explicit version coverage
and rechecking on upgrades.

Before adopting it, reproduce the malformed-intent failure and verify both its recovery and a
valid pending-intent launch. Then test success, cancellation, recreation and background/resume
with Play-installed licensed test purchases. Do not broadly catch runtime exceptions or treat
closing the broken activity as a successful purchase. Also verify the Billing version actually
used by the affected Net Probe release.

## WorkManager: no public configuration fallback for the missing method

The `2.12.0` AAR calls `JobScheduler.forNamespace("androidx.work.systemjobscheduler")` whenever
`SDK_INT >= 34`, without catching `NoSuchMethodError`. Its matching source creates the system
scheduler before returning the `WorkManagerImpl` instance. The initialization exception handler
is used by `ForceStopRunnable` for storage/direct-boot failures, not around this constructor path.
Disabling the greedy scheduler still creates the system scheduler.

Therefore, adding an exception handler, delaying initialization or changing R8 rules does not
restore the missing platform method. Glance also depends on WorkManager, so removing eager
initialization alone only moves the failure to a later widget request.

First collect the affected device's actual SDK level, build fingerprint and method availability
to resolve why an API 34 report lacks an API 34 framework method. A device-specific availability
gate could preserve foreground app access only if all WorkManager-dependent widget operations
also have an explicit unavailable path. That is a product behavior change, not a complete
scheduling fix. A maintained WorkManager fork with a non-namespaced fallback is another possible
experiment, but must account for existing namespaced jobs, cancellation and rescheduling across
upgrades. No such fork or gate was introduced here.

## Inline helper: the owner is not established by the exported frame

The resolved Kotlin `kotlin-stdlib:2.4.21` JAR contains no `InlineClassHelperKt` class. Compose UI's
`classes.jar` contains `androidx/compose/ui/internal/InlineClassHelperKt.class`, also present in
the readable deactivated-node crash. The supplied two-line export instead names
`kotlin.jvm.internal.InlineClassHelperKt`. Do not attribute it to the Kotlin runtime or merge it
with the Compose incident without the full exception message, callers and matching release map.

The `org.jetbrains.compose.ui:ui-android:1.12.1` artifact in the graph has a 259-byte empty
`classes.jar`. Its presence alongside AndroidX UI does not itself demonstrate duplicate Compose
implementation classes.
