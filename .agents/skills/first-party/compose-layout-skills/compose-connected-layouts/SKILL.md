# Compose connected layouts

Use a compatible native component for standard connected layouts. Keep project-specific design,
domain content, and custom geometry that the available components cannot express.

For related layout concerns, see the [Compose layout map](../README.md).

## Rules

- **ConnectedNativeFirst-1 (mandatory):** Before creating or modifying a connected collection, inspect the resolved Compose and Material dependencies, existing components and official APIs. Classify the layout: continuous list, segmented list, connected buttons, ordinary grid, connected grid or variable-span bento. Use the compatible native component for every supported case. For list-shaped content also apply `ListItemFirst-1` and `ListItemApi-1` in `compose-interactive-surfaces`. Reuse a project wrapper only when it delegates equivalent standardized behavior to native APIs or has a documented concrete exception. Do not reconstruct native behavior simply for custom styling or slots. Do not introduce a new dependency, experimental opt-in or public API break without an explicit need and approval where required.
- **SegmentedFirst-1 (mandatory):** For intentionally connected vertical list-shaped entries, use `SegmentedListItem`, `ListItemDefaults.segmentedShapes(index, count)` and `ListItemDefaults.SegmentedGap` on supported versions. Derive index/count from the rendered group, not the entire screen or the backing unfiltered dataset. Handle zero, one, first, middle, last, conditional entries, headers, ads and animation transitions. Use the static, click, selected or checked overload matching actual semantics. For continuous lists use `ListItem` rather than manufacturing segmentation. Do not force charts, headers, arbitrary tiles or forms into a list-item component.
- **ConnectedButton-1:** For connected horizontal actions, evaluate `ButtonGroup` and its connected defaults; for mutually exclusive or independent selections evaluate the appropriate segmented button APIs. Select by behavior, not by rounded appearance. Do not use a button group as a generic card grid.
- **ShapeOwnership-1:** Supply the intended `shape` or state-aware `shapes` directly to a Material surface when supported. Do not render a rectangular Material component and externally clip it to emulate native connected shapes. Use manual clipping for custom primitives or non-surface content only when needed. Keep visual shape, indication and interaction state coherent; follow `Shape-1` and `ActionOwner-1` from the interactive surfaces skill.
- **GroupGeometry-1:** A connected group owns tile placement, adjacency, shared gaps and exposed corners. A tile owns its content and independent action. Derive corner treatment from the planned geometry in logical start/end coordinates. For a rectangular group the four outside corners may use the outer token and internal seams the inner token. Nonrectangular or spanning arrangements need explicit perimeter rules; do not equate every non-adjacent edge with an outer convex corner. Keep geometry deterministic and testable independently of composition.
- **SharedDimensions-1:** Connected peers sharing an edge need compatible measured bounds. Establish shared row heights or track geometry instead of independently sizing and center-aligning tiles. Prefer standard `Row`, `Column`, `FlowRow` with `fillMaxRowHeight`, or grid facilities when they satisfy constraints. Use intrinsic sizing only for compatible children and bounded constraints. Do not impose fixed heights that clip large text; keep minimum touch targets and content growth intentional.
- **BentoLayout-1:** Bento denotes a visual composition with unequal tile sizes and hierarchy, not a specific Material 3 API. Prefer ordinary composition for small known arrangements, `LazyVerticalGrid` for lazy column spans, and `LazyVerticalStaggeredGrid` for masonry-like layouts. A custom `Layout` is justified only for unsupported requirements such as arbitrary two-axis spans, exact track alignment or geometry-driven grouping. Do not assume a staggered grid supports row spans. Define track sizing, spans, gap allocation, overflow, reading order and responsive fallback before implementing a custom measure policy. Measure each child once in the normal measurement pass; use intrinsic queries or subcomposition only when appropriate.
- **ShapeTokens-1:** Prefer Material component defaults and existing semantic design-system tokens. If a custom group needs outer, seam and interaction shapes, expose semantic roles with a single owner; do not add a generic parallel token framework or force all radii to be equal. Preserve brand shapes, meaningful visual hierarchy and accessibility. Distinguish icon silhouettes (`MaterialShapes`) from connected surface geometry.
- **AdaptiveGroup-1:** Recompute rows, columns, spans and corners after available width, layout direction, visibility or ordering changes. Use stable item identities for dynamic collections; do not derive shape from global indices or stale cached plans. Verify narrow and wide layouts and RTL.
- **InteractionShape-1:** Use native indication and state-aware shapes where available. Preserve disabled, selected, checked, pressed, focus and hover states as applicable. One logical action has one owner; a trailing switch/checkbox can delegate to the row (null callback when supported) or retain a separate action when required. Keep haptic feedback, gestures, accessibility and analytics contracts without duplicate callbacks. A connected appearance does not imply one shared click target.
- **VisibleGeometry-1:** Conditional entries, expandable content and ads must not leave phantom gaps, incorrect terminal corners or unstable keys. Derive the geometry from the visible/transition layout plan, while retaining any necessary nonvisual lifecycle separately. Keep ad SDK interaction, disclosure and click behavior intact.
- **MigrationCleanup-1 (mandatory):** When a native API replaces custom behavior, migrate affected call sites, then remove private/internal dead code and redundant tests or replace them with contract tests. Search source, tests, samples, docs and downstream compatibility surfaces. Follow the release's explicitly approved compatibility policy. When a breaking migration is authorized, remove obsolete public APIs and forwarding wrappers after migrating in-repository consumers; update API dumps, documentation and migration notes. Do not retain dead APIs merely for compatibility in an authorized breaking release. Otherwise preserve supported public signatures or follow the approved deprecation policy. Do not delete custom code serving a distinct unsupported requirement. Report every retained exception with evidence, and do not mass-refactor unrelated UI unless explicitly scoped.

## Workflow and review

1. Inspect current implementation, design references, dependency resolution and all consumers. Classify each affected component before editing; record native API, custom requirement and migration compatibility.
2. Select the native component and customize its slots/defaults first. Assign group spacing, content padding and surface shape to the correct owners. Load `compose-layout-spacing`, `compose-layout-constraints`, `compose-interactive-surfaces` and `compose-scroll-insets` as needed.
3. For remaining custom geometry, document why the standard APIs cannot satisfy it. Plan coordinates/track bounds and shape roles before composing tiles; avoid speculative generic APIs.
4. Validate empty/single/multiple groups, hidden/inserted/reordered items, shared edges, adaptive reflow, RTL, long localized text, font scaling, light/dark themes, touch targets, real pressed indication and keyboard/accessibility semantics. Keep behavioral contracts (callbacks, state, accessibility and side effects); change public signatures only within the approved release scope. Compile and run the project's tests and visual checks; report skipped checks explicitly.

Review findings include new or retained redundant native-equivalent implementations in the scoped migration, double action owners, outer clip/native shape conflicts, duplicate gaps, misaligned connected peers, unsupported span assumptions and unexplained exceptions. Do not treat every `Row`, `Column`, `Card` or custom `Shape` as a finding.

Read [examples](references/examples.md) for implementation patterns and boundaries.
