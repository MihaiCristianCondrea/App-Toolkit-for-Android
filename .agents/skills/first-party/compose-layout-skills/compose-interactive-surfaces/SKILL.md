# Compose interactive surfaces

For related layout concerns, see the [Compose layout map](../README.md).

## Rules

For connected lists, connected buttons, positional group shapes, grids or bento compositions, load `compose-connected-layouts` and apply `ConnectedNativeFirst-1` and the relevant geometry rules.

- **ListItemFirst-1 (mandatory):** Before implementing or changing any `Column`, `LazyColumn`, or equivalent vertical collection, classify its children. Every list-shaped entry MUST use the appropriate Material 3 `ListItem` or `SegmentedListItem` directly, or an existing project component that delegates equivalent standardized behavior to it. A project wrapper that manually duplicates a compatible native component is not an exemption. This applies to single entries, repeated rows, settings, file entries, tool entries and other leading/main/trailing content patterns, including non-clickable entries. Do not reproduce a compatible list item with a manual `Row` + `Column` + `Spacer` + padding + interaction chain. Use composable slots for custom content, existing defaults for spacing and appearance, and available parameters for customization. A raw layout is permitted only when the available component cannot satisfy a concrete layout, semantic, interaction or compatibility requirement; record the specific reason in the implementation/review summary. Aesthetic preference, unfamiliarity with slots, and the presence of custom composables are not sufficient reasons. Do not force headers, forms, arbitrary panels, charts, hero cards, spacers, dividers or other structural content into `ListItem`. This is a project convention, not a Compose API restriction.
- **ListItemApi-1:** Inspect the project's resolved Material 3 version and existing design-system components before selecting an overload. Prefer native interactive/selection overloads when available and appropriate. On older versions, use the non-interactive `ListItem` with `headlineContent` and attach the appropriate action to its root where needed. Do not introduce a duplicate action, upgrade dependencies, opt into experimental APIs or change existing design solely to satisfy the preference. Use `SegmentedListItem` only for intentionally segmented groups; derive shapes from the position within the visible group and use its version-appropriate gap/defaults. Use `contentPadding` and `verticalAlignment` when exposed; do not invent unsupported parameters or emulate internal padding with outer padding that shrinks the ripple.

- **InteractionBounds-1:** Identify the intended visual surface, indication bounds and touch target separately. For an edge-to-edge row, the root action and indication cover the available row surface, with text and icons inset inside it. Ancestor gutters limit the available surface width.
- **RippleOrder-1:** For a custom bounded clickable surface, put content padding after the interaction modifier. Padding before it is external to the indication. Actual touch input may extend beyond small measured clickable bounds due to minimum touch target expansion; never infer hit-test bounds solely from the ripple.
- **Shape-1:** Use the same intended shape for background and indication clipping. Prefer the appropriate clickable Material component (e.g. Card or Surface) when its semantics and behavior match. For manual chains, place `clip(shape)` outside the indication, then the background, then the interaction, then content padding. A shape passed only to `background` does not clip descendants or ripple.
- **ActionOwner-1:** Give each logical action one interactive owner. Do not add a second clickable to an already clickable Surface/Card/Button. Use `selectable` or `toggleable` when semantics require it; use Material controls where suitable. A separate trailing action is valid only when independently actionable and accessible. Avoid accidental overlapping actions.
- **TouchTarget-1:** Aim for at least 48 x 48 dp of usable touch target for independent touch actions on Android. Prefer sufficient measured space to avoid overlapping automatically expanded targets. Respect component defaults and parent constraints; an exact visual height is not a universal accessibility solution.
- **Indication-1:** Preserve the project's theme indication and pressed, focused, hovered, selected and disabled behavior as appropriate. Do not suppress ripple, replace it with pointerInput, or add a custom interaction source unless there is a concrete behavior requirement. Check the Compose version for current ripple APIs.
- **Semantics-1:** Preserve the correct role, enabled state, selected/checked state, and meaningful accessibility labels. Decorative icons have no independent description when the parent action already conveys their meaning. Independently actionable icons need their own label.
- **GroupShape-1:** Group spacing and corner shapes are a design decision. For supported segmented lists, delegate shape resolution and state morphing to Material (`SegmentedFirst-1` in `compose-connected-layouts`). For custom groups the parent determines geometry and gaps; each surface owns its assigned shape and indication. Do not force rounded cards or gaps onto continuous edge-to-edge lists.

## Review

For every affected vertical collection, verify list-shaped entries against `ListItemFirst-1`, including implementations hidden behind project wrappers. Treat a newly hand-built compatible list row without a concrete exception as a review finding. Do not migrate unrelated existing code or force a visual redesign. Trace the root modifier from caller padding through shape, background, interaction and content padding. Compare idle and pressed bounds. Test center and edge taps, external gap behavior, disabled state, independent actions, keyboard/focus where supported, RTL, and large text. Verify the visual ripple with a real press or screenshot; a semantics click alone does not prove ripple coverage.

Read [examples](references/examples.md) for patterns and caveats.
